# JS: промисы на практике (комбинаторы, параллелизм, отмена)

## 🎯 Зачем эта тема

Соседняя тема [03-event-loop.md](03-event-loop.md) отвечает на вопрос **«когда выполнится»**.
Эта — на вопрос **«как написать»**: реализовать обёртку, ограничить параллелизм, поставить
таймаут, отменить лишний запрос.

Формат вопросов: _«напишите свой Promise.all»_, _«запустите 100 запросов, но не больше 5
одновременно»_, _«что если запрос висит»_, _«как отменить предыдущий поиск»_.

> ⚠️ Проходи эту тему **после** event loop: почти каждое объяснение здесь опирается на порядок
> выполнения микрозадач.

## 🧠 Ключевые идеи

### 1. Промис — объект с необратимым состоянием

`pending → fulfilled | rejected`. Переход происходит **один раз**; повторные вызовы `resolve`
или `reject` молча игнорируются.

```js
new Promise((resolve, reject) => {   // executor выполняется СИНХРОННО
  resolve(1);
  resolve(2);                        // игнорируется
  reject(new Error('x'));            // тоже игнорируется
});
```

Это свойство — основа собственных комбинаторов: в `Promise.race` можно спокойно подписывать
`resolve` на все промисы сразу, «победит» первый, остальные ни на что не повлияют.

### 2. Promise constructor antipattern

`new Promise` нужен **только** для оборачивания колбэчного API. Если у тебя уже есть промис —
верни его.

```js
// ❌ лишняя обёртка: легко потерять ошибку и «подвесить» промис
function getUser(id) {
  return new Promise((resolve, reject) => {
    fetchUser(id).then(resolve).catch(reject);
  });
}

// ✅
function getUser(id) {
  return fetchUser(id);
}

// ✅ а вот здесь конструктор уместен — у setTimeout нет промис-версии
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
```

### 3. Комбинаторы: четыре штуки, знать все

| Комбинатор | Резолвится | Реджектится | Результат |
|---|---|---|---|
| `all` | все успешны | **первая** ошибка (fail-fast) | массив значений |
| `allSettled` | все завершились | никогда | массив `{status, value \| reason}` |
| `race` | первый **завершившийся** | если первый завершился ошибкой | значение/ошибка первого |
| `any` | первый **успешный** | все отклонены | значение / `AggregateError` |

Мнемоника: `all` — «все или ничего», `allSettled` — «расскажи про всех», `race` — «кто первый»,
`any` — «первый, у кого получилось».

Применение: `all` — обязательные данные экрана; `allSettled` — дашборд, где виджет может упасть;
`race` — таймаут (`race([запрос, таймер])`); `any` — запрос к нескольким зеркалам.

> ⚠️ Ни один комбинатор **не отменяет** остальные промисы. При ошибке в `all` прочие запросы
> продолжают выполняться — их результаты просто игнорируются.

### 4. Три режима параллелизма

```js
// ВСЕ СРАЗУ — быстро, но 100 одновременных запросов положат сервер
await Promise.all(urls.map(fetch));

// ПО ОДНОМУ — безопасно, но N·T вместо T
for (const url of urls) await fetch(url);

// ОГРАНИЧЕННЫЙ ПУЛ — золотая середина
await promisePool(tasks, 5);
```

**Идея пула:** запустить `limit` асинхронных «воркеров»; каждый в цикле берёт следующую задачу
по общему индексу из замыкания и работает, пока задачи не кончатся.

Важная деталь: в пул передают **функции** (`() => fetch(url)`), а не промисы. Промис стартует в
момент создания — массив готовых промисов ограничить уже невозможно.

### 5. «Перестать ждать» ≠ «отменить»

| Уровень | Что происходит | Инструмент |
|---|---|---|
| Игнорирование результата | операция идёт, ответ выбрасывается | флаг / `Promise.race` |
| Настоящая отмена | соединение закрывается | **`AbortController`** |

```js
const controller = new AbortController();
fetch(url, { signal: controller.signal });
controller.abort();          // fetch реально прерывается, бросая AbortError
```

`AbortError` нужно **отличать** от сетевой ошибки по `error.name`, иначе пользователь увидит
ложное «не удалось загрузить» при каждом нажатии клавиши.

## 📝 Эталонный разбор: `withTimeout`

Задача: если промис не успел за `ms` — отклонить.

```js
function withTimeout(promise, ms, message = `Timeout after ${ms}ms`) {
  let timeoutId;

  const timeout = new Promise((_, reject) => {
    timeoutId = setTimeout(() => reject(new Error(message)), ms);
  });

  return Promise.race([promise, timeout]).finally(() => clearTimeout(timeoutId));
}
```

**Три решения, которые нужно объяснить:**

1. **`Promise.race`** — завершается первым завершившимся промисом; если это таймер, получаем
   ошибку, если работа — её результат.
2. **`new Promise` здесь уместен** — мы оборачиваем `setTimeout`, у которого нет промис-версии.
3. **`.finally(() => clearTimeout(timeoutId))`** — снимает таймер в обоих исходах. Без этого в
   Node процесс не завершится, пока таймер не сработает. `finally` **прозрачен**: не меняет ни
   значение, ни ошибку, поэтому его безопасно вешать в конец цепочки.

И обязательная оговорка вслух:

> _«Race только перестаёт ждать — исходный запрос продолжает выполняться. Для настоящей отмены
> нужен AbortController»._

Именно эта фраза отличает «выучил рецепт» от «понимаю модель».

## ⚠️ Частые ошибки / чек-лист

- ❌ **Promise constructor antipattern** — обёртка вокруг существующего промиса.
- ❌ **`forEach` с async-колбэком** — он не ждёт промисы. Нужен `for...of` + `await`
  (последовательно) или `Promise.all(map(...))` (параллельно).
- ❌ **`await` в цикле там, где нужна параллельность** — `N·T` вместо `T`.
- ❌ **`try/catch` без `await`** — синхронный `catch` не поймает отклонение промиса.
- ❌ **Забыть, что `all` падает на первой ошибке** — если нужны все результаты, `allSettled`.
- ❌ **Передать в пул промисы вместо функций** — они уже стартовали, ограничивать нечего.
- ❌ **Не чистить таймер** после `race` — висящий `setTimeout`.
- ❌ **Считать, что `race` отменяет проигравший промис** — не отменяет.
- ❌ **Путать `AbortError` с реальной ошибкой** — ложные сообщения пользователю.
- ✅ Уточняй: «сколько параллельных запросов допустимо?», «нужен fail-fast или собрать всё?»,
  «нужно ли отменять предыдущий запрос?».

## ✅ Мини-опрос для самопроверки

1. Что произойдёт при повторном вызове `resolve` в одном промисе?
2. Когда `new Promise` уместен, а когда это антипаттерн?
3. Чем `all` отличается от `allSettled`, `race` и `any`?
4. Почему в `promisePool` передают функции, а не промисы?
5. Отменяет ли `Promise.race` проигравшую операцию? Как отменить по-настоящему?
6. Почему `try/catch` не ловит ошибку из `api.post('/save')` без `await`?

<details>
<summary>Ответы</summary>

1. Ничего: состояние промиса меняется **один раз** и необратимо, повторные `resolve`/`reject`
   игнорируются. На этом свойстве строятся комбинаторы вроде `race`, где `resolve`
   подписывается сразу на все промисы.
2. Уместен для **оборачивания колбэчного API** без промис-версии (`setTimeout`, старый
   `fs.readFile`, события). Антипаттерн — оборачивать то, что уже возвращает промис: лишний
   код, риск потерять ошибку и «подвесить» внешний промис навсегда.
3. `all` — ждёт все, падает на первой ошибке, отдаёт массив значений. `allSettled` — ждёт все,
   никогда не падает, отдаёт массив `{status, value|reason}`. `race` — первый **завершившийся**
   (успех или ошибка). `any` — первый **успешный**, а если все упали — `AggregateError`.
4. Промис стартует в момент создания. Массив готовых промисов означает, что все операции уже
   запущены, и ограничивать параллелизм поздно. Функция `() => task()` откладывает старт до
   момента, когда освободится «воркер».
5. Нет — `race` лишь перестаёт ждать, проигравшая операция продолжает выполняться, а её
   результат игнорируется. Настоящая отмена — `AbortController`: `signal` передаётся в `fetch`,
   `abort()` закрывает соединение и бросает `AbortError`.
6. Синхронный `try/catch` ловит только то, что бросается **во время выполнения блока**.
   `api.post` возвращает промис немедленно, а отклонение происходит позже — блок `try` к тому
   моменту завершён. Нужен либо `await` внутри `try`, либо `.catch()`.

</details>
