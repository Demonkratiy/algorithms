# Recursion & Call Stack (рекурсия)

## 🎯 Идея

**Рекурсия** — функция вызывает саму себя на «уменьшенной» версии задачи, пока не дойдёт до
случая, ответ на который известен сразу.

Любая рекурсивная функция состоит из двух частей:

```js
function solve(input) {
  if (/* базовый случай */) return /* известный ответ */;   // 1. BASE CASE

  return /* комбинация */ solve(/* уменьшенный input */);   // 2. РЕКУРСИВНЫЙ ШАГ
}
```

Без базового случая — бесконечный спуск и `RangeError: Maximum call stack size exceeded`.
Без «уменьшения» входа — то же самое.

> 💡 **Главный навык — доверять рекурсии.** Не пытайся мысленно раскрутить весь стек вызовов.
> Считай, что вложенный вызов **уже вернул правильный ответ** для меньшей задачи, и думай
> только о том, что делать с этим ответом на текущем уровне. Это называется «рекурсивный
> контракт», и именно так рассуждают опытные разработчики.

---

## 🧠 Как распознать (ментальная модель)

Рекурсия уместна, когда:
- задача **сводится к себе же** меньшего размера: `f(n)` выражается через `f(n-1)`;
- структура данных **рекурсивна по природе**: дерево, вложенные объекты, DOM, JSON, файловая
  система (у узла есть потомки того же типа);
- нужен **перебор всех вариантов**: подмножества, перестановки, комбинации → backtracking;
- «разделяй и властвуй»: merge sort, quick sort, бинарный поиск.

### Три шаблона, которые надо узнавать

**1. Линейная рекурсия** — один вызов внутри. Легко переписывается в цикл.
```js
function factorial(n) {
  if (n <= 1) return 1;             // база
  return n * factorial(n - 1);      // один вызов
}
```

**2. Древовидная рекурсия** — два и более вызовов. Тут появляется экспоненциальный рост и
необходимость **мемоизации**.
```js
function fib(n) {
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2);   // два вызова → дерево вызовов
}
```

**3. Backtracking (перебор с возвратом)** — строим решение по шагу, откатываемся и пробуем
другой вариант.
```js
function backtrack(path, choices) {
  if (/* решение готово */) { result.push([...path]); return; }   // копия!

  for (const choice of choices) {
    path.push(choice);           // выбрали
    backtrack(path, /* оставшиеся */);
    path.pop();                  // ОТКАТИЛИ — это и есть "backtracking"
  }
}
```

## ⏱️ Сложность рекурсии

**Время** = (количество вызовов) × (работа внутри одного вызова).
**Память** = глубина стека × размер фрейма (+ то, что аллоцируется внутри).

| Пример | Время | Память |
|---|:---:|:---:|
| `factorial(n)` | `O(N)` | `O(N)` стек |
| `fib(n)` наивно | `O(2^N)` | `O(N)` стек |
| `fib(n)` с мемоизацией | `O(N)` | `O(N)` |
| Бинарный поиск рекурсивно | `O(log N)` | `O(log N)` |
| Merge sort | `O(N log N)` | `O(N)` |
| Все подмножества | `O(N · 2^N)` | `O(N)` стек + `O(N·2^N)` ответ |
| Все перестановки | `O(N · N!)` | `O(N)` стек |

> ⚠️ **Про память забывают чаще всего.** Даже если рекурсия не создаёт массивов, она тратит
> `O(глубина)` на стек вызовов. Это обязательная часть ответа на вопрос «какая сложность?».

### Наглядно: почему наивный `fib` — это `O(2^N)`

```
                fib(5)
            /            \
        fib(4)          fib(3)
       /     \          /     \
   fib(3)   fib(2)  fib(2)   fib(1)
   /   \
fib(2) fib(1)   ...
```

`fib(3)` вычисляется дважды, `fib(2)` — трижды. Дерево вызовов удваивается на каждом уровне →
примерно `2^N` вызовов. **Мемоизация** (кеш уже посчитанных значений) убирает повторы и делает
`O(N)`.

### Стек вызовов и его предел

В JS глубина стека ограничена (~10 000–15 000 фреймов в V8, точное число зависит от движка и
размера фрейма). Признак проблемы:

```
RangeError: Maximum call stack size exceeded
```

Что делать:
1. проверить **базовый случай** (чаще всего дело в нём);
2. убедиться, что вход реально **уменьшается** на каждом шаге;
3. если рекурсия корректна, но глубина велика — **переписать в цикл** с явным стеком.

> 📝 Про хвостовую рекурсию (tail call optimization): она есть в спецификации ES6, но
> **фактически не реализована** ни в V8, ни в других основных движках (только Safari/JSC).
> Полагаться на неё в JS нельзя — хорошая деталь для устного ответа.

## 📝 Эталонный разбор

### Задача: Fibonacci с мемоизацией

`fib(0) = 0`, `fib(1) = 1`, `fib(n) = fib(n-1) + fib(n-2)`.

**Шаг 1. Наивно (как думаем сначала):**
```js
function fib(n) {
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2);
}
```
Время `O(2^N)`, память `O(N)`. `fib(45)` будет считаться минутами.

**Шаг 2. Что не так.** Одни и те же подзадачи считаются многократно. Решение — **запомнить**
результат (мемоизация, это top-down динамическое программирование).

**Шаг 3. С мемоизацией:**
```js
function fib(n, memo = new Map()) {
  if (n < 2) return n;                    // база
  if (memo.has(n)) return memo.get(n);    // уже считали — берём готовое

  const result = fib(n - 1, memo) + fib(n - 2, memo);
  memo.set(n, result);                    // запоминаем перед возвратом
  return result;
}
```
Время **`O(N)`** — каждое значение считается ровно один раз. Память `O(N)` — кеш плюс стек.

**Шаг 4. Итеративно (лучшее по памяти):**
```js
function fibIterative(n) {
  if (n < 2) return n;

  let prev = 0;
  let curr = 1;
  for (let i = 2; i <= n; i++) {
    [prev, curr] = [curr, prev + curr];
  }
  return curr;
}
```
Время `O(N)`, память **`O(1)`**. Ни рекурсии, ни кеша.

> 💬 Формулировка для интервью: _«Наивная рекурсия — O(2^N) из-за повторных подзадач. Добавляю
> мемоизацию — O(N) время, O(N) память. А поскольку нужны только два последних значения, можно
> свести к итерации с O(1) памяти»._ Это полный ответ по задаче.

### ⚠️ Ловушка с параметром по умолчанию

```js
function bad(n, memo = new Map()) { ... }   // ✅ новый Map при каждом ВНЕШНЕМ вызове
```
Это корректно: значение по умолчанию вычисляется при каждом вызове без аргумента, а внутренние
рекурсивные вызовы **передают `memo` явно**. Забыть передать `memo` внутрь — типичная ошибка:
кеш будет создаваться заново на каждом уровне и мемоизация не сработает (тихая потеря
производительности без ошибки — заметить трудно).

## ⚠️ Частые ошибки / чек-лист

- ❌ **Нет базового случая** или он недостижим → `Maximum call stack size exceeded`.
- ❌ **Вход не уменьшается**: `solve(n)` вместо `solve(n - 1)`.
- ❌ **Забыть `return`** перед рекурсивным вызовом → функция вернёт `undefined`.
  Очень частая опечатка: `solve(n - 1)` вместо `return solve(n - 1)`.
- ❌ **Не передать мемо/аккумулятор** во вложенный вызов.
- ❌ **Забыть `path.pop()`** в backtracking → варианты «слипаются».
- ❌ **Положить в результат ссылку, а не копию**: `result.push(path)` вместо
  `result.push([...path])`. Потом `path` изменится, и в ответе окажутся одинаковые/пустые
  массивы. **Это ошибка №1 в задачах на перебор.**
- ❌ **Забыть про память стека** при оценке сложности.
- ✅ Проверяй рекурсию на **самом маленьком** входе (`n = 0`, `n = 1`, пустой массив) — база
  ломается именно там.

## ✅ Мини-опрос для самопроверки

1. Из каких двух обязательных частей состоит любая рекурсивная функция?
2. Почему наивный `fib(n)` работает за `O(2^N)`, а с мемоизацией — за `O(N)`?
3. Какова сложность **по памяти** у рекурсии, которая не создаёт никаких структур данных?
4. Что означает `RangeError: Maximum call stack size exceeded` и что проверять в первую очередь?
5. Зачем в backtracking нужна строка `path.pop()` и что будет без неё?
6. Почему в результат кладут `[...path]`, а не `path`?

<details>
<summary>Ответы</summary>

1. **Базовый случай** (условие остановки с известным ответом) и **рекурсивный шаг**, который
   вызывает функцию на строго меньшем входе и комбинирует результат.
2. Наивная версия пересчитывает одни и те же подзадачи: дерево вызовов ветвится надвое на каждом
   уровне → ~`2^N` вызовов. Мемоизация сохраняет результат для каждого `n`, поэтому каждое
   значение вычисляется ровно один раз → `N` вызовов, `O(N)`.
3. `O(глубина рекурсии)` — каждый незавершённый вызов держит фрейм в стеке. Для линейной
   рекурсии это `O(N)`, для бинарного поиска — `O(log N)`, для обхода сбалансированного
   дерева — `O(log N)`, несбалансированного — `O(N)`.
4. Глубина стека превысила лимит движка. Проверять: (1) есть ли базовый случай и достижим ли он,
   (2) уменьшается ли аргумент на каждом шаге, (3) если всё верно — глубина объективно велика,
   и нужно переписать на цикл с явным стеком.
5. `pop()` **откатывает** последний выбор, чтобы на этом уровне можно было попробовать
   следующий вариант с чистым состоянием. Без него `path` накапливает элементы из всех веток и
   результаты будут неверными.
6. `path` — один и тот же массив, который постоянно мутируется. Положив ссылку, ты получишь в
   результате `N` ссылок на **один** массив, который к концу работы окажется пустым.
   `[...path]` создаёт **снимок** текущего состояния.

</details>
