# Event Loop и асинхронность

## 🎯 Зачем это

Самая частая **теоретическая** секция FE-интервью. Спрашивают в двух форматах:

1. **«Что выведется?»** — сниппет с `setTimeout`, `Promise.then` и `await`, надо назвать порядок.
2. **«Реализуйте»** — `sleep`, `retry`, `withTimeout`, отменяемый запрос.

Оба формата проверяют одно: понимаешь ли ты, **когда именно** выполняется отложенный код.
Это же знание объясняет реальные баги — подвисший интерфейс, гонки запросов, «почему состояние
обновилось не сразу».

---

## 🧠 Модель: стек, очереди, цикл

JS **однопоточен**: в каждый момент выполняется ровно одна функция. Асинхронность обеспечивают
не потоки, а **окружение** (браузер / Node) и очереди задач.

```
   ┌─────────────┐
   │  Call Stack │  ← выполняется прямо сейчас
   └──────┬──────┘
          │ пусто?
          ▼
   ┌──────────────────┐
   │ Microtask Queue  │  ← выгребается ЦЕЛИКОМ
   │ .then / await /  │
   │ queueMicrotask   │
   └──────┬───────────┘
          │ пусто?
          ▼
   ┌──────────────────┐
   │  Macrotask Queue │  ← берётся РОВНО ОДНА задача
   │ setTimeout /     │
   │ события / I/O    │
   └──────────────────┘
          └──── и снова к микрозадачам
```

### Главное правило (запомнить дословно)

> Сначала выполняется **весь синхронный код**. Затем **полностью** опустошается очередь
> микрозадач — включая те, что появились во время её обработки. И только потом берётся
> **одна** макрозадача, после которой снова выгребаются все микрозадачи.

### Что куда попадает

| Микрозадачи (microtask) | Макрозадачи (macrotask / task) |
|---|---|
| `.then` / `.catch` / `.finally` | `setTimeout`, `setInterval` |
| продолжение после `await` | обработчики DOM-событий |
| `queueMicrotask()` | сетевые колбэки, I/O |
| `MutationObserver` | `setImmediate` (Node) |
| `process.nextTick` (Node, ещё приоритетнее) | рендеринг кадра |

**Микрозадачи всегда приоритетнее макрозадач**, сколько бы их ни было. Из этого следует важный
для фронтенда вывод: бесконечно порождающая себя цепочка `.then` **заблокирует интерфейс
навсегда** — до макрозадач и до отрисовки дело просто не дойдёт.

## 📝 Эталонный разбор

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve()
  .then(() => console.log('3'))
  .then(() => console.log('4'));

queueMicrotask(() => console.log('5'));

console.log('6');
```

### Пошаговая трассировка

| Шаг | Что происходит | Вывод | Очередь микрозадач |
|:---:|---|:---:|---|
| 1 | синхронный `console.log('1')` | **1** | — |
| 2 | `setTimeout` → в макроочередь | | — |
| 3 | промис уже выполнен → `.then(3)` в микроочередь | | `[3]` |
| 4 | `queueMicrotask` | | `[3, 5]` |
| 5 | синхронный `console.log('6')` | **6** | `[3, 5]` |
| 6 | стек пуст → берём `3` | **3** | `[5]` → `.then(4)` добавляется: `[5, 4]` |
| 7 | берём `5` | **5** | `[4]` |
| 8 | берём `4` | **4** | `[]` |
| 9 | микроочередь пуста → одна макрозадача | **2** | |

**Ответ: `1, 6, 3, 5, 4, 2`**

Два нюанса, которые здесь видно:
- второй `.then(4)` попал в очередь **после** `5`, потому что он создаётся только когда
  выполнится первый `.then` — цепочка растёт по мере обработки;
- `setTimeout(…, 0)` отработал последним, хотя задержка нулевая: **микрозадачи всегда вперёд**.

## 🔀 `async` / `await` — это промисы под сахаром

Правило из двух пунктов:

1. Тело `async`-функции выполняется **синхронно** до первого `await`.
2. Всё, что после `await`, — это **микрозадача** (эквивалент `.then`).

```js
async function f() {
  console.log('A');        // синхронно
  await null;              // await даже не-промиса ставит продолжение в микроочередь
  console.log('B');        // микрозадача
}

f();
console.log('C');
// A, C, B
```

Эквивалент на промисах:

```js
function f() {
  console.log('A');
  return Promise.resolve(null).then(() => {
    console.log('B');
  });
}
```

> ⚠️ `await` **не блокирует** поток — он «замораживает» только текущую async-функцию, отдавая
> управление наружу. Формулировка «await останавливает выполнение» на интервью считается
> ошибкой: останавливается функция, а не движок.

### Классическая головоломка

```js
async function async1() {
  console.log('async1 start');
  await async2();
  console.log('async1 end');
}
async function async2() {
  console.log('async2');
}

console.log('script start');
setTimeout(() => console.log('setTimeout'), 0);
async1();
new Promise((resolve) => {
  console.log('promise1');
  resolve();
}).then(() => console.log('promise2'));
console.log('script end');
```

**Ответ:** `script start` → `async1 start` → `async2` → `promise1` → `script end` →
`async1 end` → `promise2` → `setTimeout`

Ключ к разбору: `async1 start` и `async2` печатаются **синхронно** (до первого `await` включая
вызов внутри него), исполнитель `new Promise` тоже **синхронен**, а `async1 end` и `promise2`
— микрозадачи в порядке постановки.

> 📝 В старых движках (Chrome < 73, Node < 12) `await` стоил три микротика вместо одного, и
> `promise2` печатался раньше `async1 end`. Если увидишь такой ответ в старой статье — он не
> ошибочный, а устаревший. Хорошая деталь, чтобы упомянуть.

## ⏱️ Про таймеры

- `setTimeout(fn, 0)` — не «сразу»: минимальная задержка **≥ 4 мс** при вложенности больше пяти
  (требование спецификации HTML), плюс ожидание освобождения очереди.
- Указанная задержка — это **минимум**, а не гарантия. Если стек занят, колбэк опоздает.
- `setInterval` может «слипаться»: если колбэк выполняется дольше интервала, задачи копятся.
  Безопаснее рекурсивный `setTimeout`.

```js
// колбэк гарантированно не запустится, пока не завершится предыдущий
function tick() {
  doWork();
  setTimeout(tick, 1000);
}
```

### Node.js: три отличия

- `process.nextTick()` — **отдельная очередь**, выполняется **до** промис-микрозадач;
- `setImmediate()` — макрозадача фазы `check`, обычно раньше таймеров внутри I/O-колбэка;
- на верхнем уровне порядок `setTimeout(0)` и `setImmediate` **недетерминирован** — это
  известный вопрос-подвох.

Для FE-собеседования достаточно знать сам факт различий и что микрозадачи ведут себя одинаково.

### Рендеринг (важно для фронтенда)

Браузер может отрисовать кадр только **между макрозадачами**. Отсюда:

- долгая синхронная функция или бесконечная цепочка микрозадач → **интерфейс замирает**;
- анимации делают через `requestAnimationFrame` (вызывается перед отрисовкой кадра), а не через
  `setTimeout`;
- тяжёлые вычисления либо разбивают на куски через `setTimeout` / `scheduler.yield`, либо
  выносят в Web Worker.

## ⚠️ Частые ошибки / чек-лист

- ❌ **«`setTimeout(fn, 0)` выполнится сразу»** — нет, только после всего синхронного кода и
  **всех** микрозадач.
- ❌ **«`await` блокирует поток»** — блокирует только свою async-функцию.
- ❌ **`forEach` с `async`-колбэком** — `forEach` не ждёт промисы, код пойдёт дальше сразу.
  Нужен `for...of` с `await` (последовательно) или `Promise.all(map(...))` (параллельно).
- ❌ **`await` в цикле там, где нужна параллельность** — превращает `N` запросов из `~T` в `N·T`.
- ❌ **Забыть `await` перед вызовом** — функция вернёт промис, а не значение; `try/catch` его не
  поймает, и получишь unhandled rejection.
- ❌ **Promise constructor antipattern** — оборачивать уже существующий промис в
  `new Promise(...)` вместо того, чтобы вернуть его напрямую.
- ❌ **`try/catch` вокруг `.then`** — синхронный `catch` не ловит асинхронные ошибки.
  Нужен `.catch()` или `try/catch` вокруг `await`.
- ✅ Проговаривай ответ по шагам: «сначала синхронное, потом все микрозадачи, потом одна
  макрозадача» — интервьюер оценивает рассуждение, а не угаданный список.

## ✅ Мини-опрос для самопроверки

1. Сформулируй правило порядка выполнения (синхронный код, микро-, макрозадачи).
2. Что попадает в микроочередь, а что в макроочередь? По три примера.
3. Что выведет `setTimeout(() => console.log(1), 0); Promise.resolve().then(() => console.log(2));`?
4. Где заканчивается синхронная часть `async`-функции?
5. Почему `array.forEach(async (x) => await f(x))` не работает как ожидается?
6. Как бесконечная цепочка `.then` влияет на отрисовку страницы и почему?

<details>
<summary>Ответы</summary>

1. Выполняется весь синхронный код → **полностью** опустошается очередь микрозадач (включая
   добавленные по ходу) → берётся **одна** макрозадача → снова все микрозадачи → и так по кругу.
2. Микрозадачи: `.then/.catch/.finally`, продолжение после `await`, `queueMicrotask`
   (плюс `MutationObserver`, `process.nextTick` в Node).
   Макрозадачи: `setTimeout`/`setInterval`, обработчики DOM-событий, I/O-колбэки
   (плюс `setImmediate` в Node).
3. `2`, затем `1`. Микрозадача выполняется раньше макрозадачи, несмотря на нулевую задержку.
4. На первом `await`: всё до него выполняется синхронно в момент вызова, всё после —
   микрозадачей. Аргумент самого `await` (например, вызов `async2()`) тоже вычисляется
   синхронно.
5. `forEach` игнорирует возвращаемые промисы: он вызывает колбэк и сразу идёт дальше, ничего не
   ожидая. Код после цикла выполнится до завершения операций. Нужен `for...of` с `await`
   (последовательно) или `await Promise.all(array.map(f))` (параллельно).
6. Отрисовка возможна только между макрозадачами. Микроочередь выгребается **целиком** перед
   тем, как взять следующую макрозадачу, поэтому самовоспроизводящаяся цепочка `.then`
   не даст циклу дойти до рендеринга — страница «зависнет», хотя формально код не блокирующий.

</details>
