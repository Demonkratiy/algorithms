# Throttle (leading + trailing)

**Тема:** js-interview / function-utils · **Сложность:** medium · **Приоритет:** 🔴 основная

> Сначала реши [Throttle (leading)](02-throttle.md). Здесь отдельный контракт и отдельная
> проверка: нужно не потерять последнее событие внутри окна.

## Условие

Реализуй `throttleTrailing(fn, interval)`:

- Первый вызов выполняет `fn` **синхронно** (leading).
- Внутри окна длины `interval` вызовы не выполняются сразу; сохраняется только **последний**.
- На границе текущего окна сохранённый вызов выполняется (trailing).
- Этот фактический trailing-вызов открывает **новое полное окно**.
- Если пропущенных вызовов не было, trailing не нужен. После тишины таймеры завершаются.

`interval` — положительное целое число. Аргументы и `this` каждого выполняемого вызова
сохраняются; несколько обёрток независимы. Обёртка без новых событий не должна бесконечно
создавать таймеры.

Возврат результата `fn`, методы `cancel` / `flush`, reentrant callback и исключения в эту
задачу не входят. Это не полная совместимость с lodash.

## Примеры

Для `interval = 100` время отсчитывается относительно первого вызова:

| Время | Событие | Фактический вызов |
|---|---|---|
| 0 | `t('a')` | `'a'` сразу |
| 20 | `t('b')` | пока нет |
| 90 | `t('c')` | пока нет, `'b'` заменяется на `'c'` |
| 100 | граница окна | `'c'`, новое окно до 200 |
| 110 | `t('d')` | пока нет |
| 200 | граница окна | `'d'`, новое окно до 300 |
| 300 | граница окна | ничего: новых событий нет |

Если был лишь один `t('a')`, выполнится только `'a'` в `t=0`.
Не добавляй безусловный повтор на `t=100`.

## 🧠 Ментальная модель

Здесь два разных состояния: **окно закрыто для немедленного вызова** и **есть сохранённое
событие**. Они не эквивалентны: окно может быть активно без pending-вызова.

В отличие от debounce, новое событие **не сдвигает границу** текущего окна.
При непрерывном потоке будет не только первый и последний вызов всей серии:
будут регулярные вызовы на границах окон.

## ⚠️ Подводные камни

1. Сброс таймера на каждом событии превращает задачу в debounce.
2. После trailing нельзя сразу разрешать следующий leading: иначе расстояние между
   фактическими вызовами окажется меньше `interval`.
3. Хранить нужно последние **аргументы и `this`**, а не только значение первого аргумента.
4. Вызов без аргументов тоже может ожидать выполнения. Не используй truthiness
   `args[0]` как признак pending.
5. После выполнения pending нужно очистить. Иначе последнее событие будет повторяться.

## 💡 Подсказки

<details>
<summary>Подсказка 1 — какое состояние нужно?</summary>

Отдельно отслеживай активное окно и последний пропущенный вызов. Состояние должно
принадлежать конкретной обёртке.

</details>

<details>
<summary>Подсказка 2 — граница окна</summary>

Когда окно закончилось, проверь pending. Если он есть, выполни его и начни новое окно.
Если нет — остановись. Проследи руками событие через 10 мс после trailing.

</details>

## 🧮 Моя оценка сложности

- Время: `O(?)` — объясни, что считаешь и от каких величин зависит оценка.
- Дополнительная память: `O(?)` — отдельно оцени временные данные вызова и состояние между вызовами.

## 🧮 Самопроверка

- [ ] первый вызов синхронный
- [ ] одиночный вызов не дублируется
- [ ] последнее событие выполняется на исходной границе, не на `lastEvent + interval`
- [ ] trailing открывает новое окно
- [ ] последние `this` и все аргументы сохраняются
- [ ] обёртки независимы
- [ ] после тишины не осталось бесконечной цепочки таймеров
- [ ] объяснены время и память

**Цель по сложности:** `O(A)` по времени обработки вызова и удерживаемой памяти, где
`A` — число последних аргументов. Управление одним окном — `O(1)`. Стоимость `fn` и внутренних
структур системных таймеров не учитываем. Не храни очередь всех пропущенных событий.

Автопроверка использует виртуальные часы и проверяет наблюдаемое поведение, а не статически
выбранный алгоритм. Прошедшие тесты сами по себе не доказывают Big O.

## 🔍 Разбор — открывай ТОЛЬКО после своей попытки

<details>
<summary>Решение и трассировка</summary>

```js
function throttleTrailing(fn, interval) {
  let timer = null;
  let pending = null;

  function expire() {
    timer = null;
    if (pending === null) return;

    const { receiver, args } = pending;
    pending = null;
    timer = setTimeout(expire, interval);
    fn.apply(receiver, args);
  }

  return function (...args) {
    if (timer !== null) {
      pending = { receiver: this, args };
      return;
    }

    timer = setTimeout(expire, interval);
    fn.apply(this, args);
  };
}
```

Таймер относится к **окну**, а не к последнему событию. При замене pending таймер не меняется.
В `expire` pending очищается до вызова `fn`, а новое окно открывается при каждом фактическом
trailing. Следующее событие через 10 мс уже попадёт в это окно и дождётся его конца.

Для примера выше фактические вызовы: `'a'@0`, `'c'@100`, `'d'@200`.
На `t=300` pending отсутствует: новый таймер не создаётся, обёртка снова готова к leading.

</details>
