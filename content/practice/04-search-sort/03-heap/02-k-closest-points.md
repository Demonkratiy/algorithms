# K Closest Points to Origin

**Тема:** heap / выбор алгоритма · **Сложность:** medium · **Приоритет:** ⚪ дополнительная

> Задача-«витрина»: одна постановка, три разных решения с разной сложностью. Именно такие
> задачи проверяют, умеешь ли ты **обосновывать выбор**, а не просто писать код.

## Условие

Дан массив точек `points`, где `points[i] = [x, y]`, и число `k`.
Верни `k` точек, **ближайших к началу координат** `(0, 0)`.

Расстояние — евклидово: `√(x² + y²)`. Порядок ответа не важен.

## Примеры

```
Вход:  points = [[1, 3], [-2, 2]], k = 1
Выход: [[-2, 2]]
       // √10 ≈ 3.16  против  √8 ≈ 2.83

Вход:  points = [[3, 3], [5, -1], [-2, 4]], k = 2
Выход: [[3, 3], [-2, 4]]
```

## Ограничения

- `1 <= k <= points.length <= 10^4`
- `-10^4 <= x, y <= 10^4`

## 🎯 Три подхода — знать все

| Подход | Время | Память | Когда лучше |
|---|:---:|:---:|---|
| Сортировка по расстоянию | `O(N log N)` | `O(N)` | простой базовый ответ |
| **Max-heap размера k** | **`O(N log k)`** | **`O(k)`** | `k << N`, поток данных |
| Quickselect | `O(N)` средн. | `O(1)` | оптимально по времени |

## 🧠 Ментальная модель

**Ключевая оптимизация:** сравнивать можно **квадраты** расстояний `x² + y²` — извлекать корень
не нужно. `√a < √b` эквивалентно `a < b` для неотрицательных чисел. Это экономит `N` вызовов
`Math.sqrt` и убирает погрешность вычислений с плавающей точкой.

**Почему для «k ближайших» нужен MAX-heap** (контринтуитивно!): держим в куче `k` **лучших**
кандидатов; чтобы выбрасывать худшего из них, нужен быстрый доступ к **максимальному**
расстоянию. Отсюда max-heap размера `k`:

```
для каждой точки:
   push в кучу
   если размер > k → pop (выбрасываем самую ДАЛЁКУЮ из отобранных)
в конце в куче ровно k ближайших
```

Симметрично: для «k наибольших элементов» нужен **min**-heap. Запомни это правило —
**куча всегда противоположна тому, что ищешь**.

## ⚠️ Подводные камни именно этой задачи

1. **`Math.sqrt` не нужен.** Лишние вычисления и риск неточности. Скажи об этом вслух —
   маленькая, но заметная деталь.
2. **Max-heap, а не min-heap** (см. выше). Самая частая логическая ошибка в задаче.
3. **Выбрасывать сразу после вставки.** Порядок «push → если size > k, pop» держит кучу
   размера `k` и даёт `O(N log k)`. Если сначала набрать все `N`, получится `O(N log N)` —
   вся выгода пропадёт.
4. **В JS кучи нет** — либо пишешь свою (см.
   [01-implement-min-heap](01-implement-min-heap.md)), либо честно говоришь, что взял бы
   библиотеку, и показываешь сортировочное решение.
5. **Компаратор при сортировке обязателен** и сравнивает расстояния, а не сами массивы точек.
6. `k === points.length` — вернуть все точки; проверь, что код не ломается.

## 🔍 Разбор — открывай ТОЛЬКО после своей попытки

<details>
<summary>Вариант 1 — сортировка (базовый ответ)</summary>

```js
function kClosest(points, k) {
  const distance = ([x, y]) => x * x + y * y;      // без Math.sqrt

  return [...points]
    .sort((a, b) => distance(a) - distance(b))
    .slice(0, k);
}
```

`[...points]` — копия, чтобы не мутировать вход (`sort` изменяет массив на месте).

**Сложность:** время `O(N log N)`, память `O(N)`.

Небольшая оптимизация: если точек очень много, стоит предпосчитать расстояния один раз
(`points.map(p => [distance(p), p])`), иначе компаратор вызовет `distance` порядка `N log N` раз.

</details>

<details>
<summary>Вариант 2 — max-heap размера k</summary>

```js
function kClosestHeap(points, k) {
  const distance = ([x, y]) => x * x + y * y;

  // max-heap: наибольшее расстояние в корне
  const heap = new MinHeap((a, b) => distance(b) - distance(a));

  for (const point of points) {
    heap.push(point);
    if (heap.size > k) heap.pop();       // выбрасываем самую ДАЛЁКУЮ из отобранных
  }

  const result = [];
  while (heap.size > 0) result.push(heap.pop());
  return result;
}
```

**Почему это `O(N log k)`.** Куча никогда не превышает `k` элементов, значит каждая операция
стоит `log k`, а не `log N`. При `N = 10^4` и `k = 5` это разница между ~14 и ~2 сравнениями на
элемент.

**Инвариант:** после обработки каждой точки в куче лежат `k` ближайших из просмотренных, а в её
корне — худшая (самая далёкая) из них. Поэтому решение «оставить или выбросить» принимается за
`O(1)` сравнение.

**Главное преимущество** — память `O(k)` и работа с **потоком**: точки можно обрабатывать по
одной, не храня весь массив. Именно это стоит проговорить на интервью.

</details>

<details>
<summary>Вариант 3 — quickselect (оптимально по времени)</summary>

```js
function kClosestQuickselect(points, k) {
  const distance = ([x, y]) => x * x + y * y;

  function partition(left, right) {
    const pivotIndex = left + Math.floor(Math.random() * (right - left + 1));
    [points[pivotIndex], points[right]] = [points[right], points[pivotIndex]];

    const pivotDist = distance(points[right]);
    let boundary = left;

    for (let i = left; i < right; i++) {
      if (distance(points[i]) <= pivotDist) {
        [points[i], points[boundary]] = [points[boundary], points[i]];
        boundary++;
      }
    }

    [points[boundary], points[right]] = [points[right], points[boundary]];
    return boundary;
  }

  let left = 0;
  let right = points.length - 1;

  while (left <= right) {
    const p = partition(left, right);
    if (p === k) break;                 // первые k элементов — искомые
    if (p < k) left = p + 1;
    else right = p - 1;
  }

  return points.slice(0, k);
}
```

Та же идея, что в [Kth Largest](../02-sorting/03-kth-largest.md): после разбиения мы знаем
финальную позицию pivot и рекурсивно спускаемся **только в нужную половину**. Средняя сложность
`O(N)` (`N + N/2 + N/4 + ... = 2N`), худшая `O(N²)` — лечится случайным pivot.

Минус: мутирует входной массив и не работает с потоком.

</details>
