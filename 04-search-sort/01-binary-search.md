# Binary Search (бинарный поиск)

## 🎯 Идея

Если данные **упорядочены**, то, сравнив элемент в середине с искомым, можно **выбросить
половину** вариантов за одно сравнение. Повторяя, доходим до ответа за `O(log N)`.

`log₂(1 000 000) ≈ 20` — миллион элементов проверяется за 20 шагов вместо миллиона. Именно
поэтому бинарный поиск — любимый способ интервьюера проверить, умеешь ли ты «переходить от
`O(N)` к `O(log N)`».

```
Ищем 7 в [1, 3, 5, 7, 9, 11]
  l=0, r=5, mid=2 → 5 < 7 → выбрасываем левую половину, l = 3
  l=3, r=5, mid=4 → 9 > 7 → выбрасываем правую, r = 3
  l=3, r=3, mid=3 → 7 === 7 ✅
```

---

## 🧠 Как распознать (ментальная модель)

### 1. Явный признак — «массив отсортирован»
Если в условии сказано «sorted» и просят что-то найти — почти наверняка бинарный поиск.
Если сказано «сделайте за `O(log N)`» — это прямое указание.

### 2. Неявный признак — бинарный поиск **по ответу** (важнее!)
Массив может быть не отсортирован вовсе. Ключевой вопрос:

> **«Можно ли для конкретного кандидата X быстро проверить, подходит ли он, и верно ли, что
> если X подходит, то всё, что больше X, тоже подходит?»**

Если ответ «да» — пространство ответов **монотонно**, и по нему можно искать бинарно:

```
X:        1   2   3   4   5   6   7   8
подходит: ✗   ✗   ✗   ✓   ✓   ✓   ✓   ✓
                     ↑ ищем эту границу
```

Формулировки-маркеры: «**минимальное** значение, при котором…», «**максимальная** скорость, при
которой…», «минимальное количество дней/кораблей», «первая плохая версия».

Это и есть главный boost по темe: половина «сложных» задач с binary search — это задачи, где
массива-то и нет.

### 3. Три разновидности, которые надо уметь писать
| Вариант | Что ищем | Ключевое отличие |
|---|---|---|
| Классический | точное совпадение | `while (l <= r)`, при совпадении `return mid` |
| Граница (lower/upper bound) | **первый** элемент, удовлетворяющий условию | `while (l < r)`, ответ не теряем, сдвигая `r = mid` |
| По ответу | минимальный/максимальный валидный X | вместо массива — функция-проверка `isFeasible(X)` |

---

## ⏱️ Сложность

- Время **`O(log N)`** — на каждом шаге отбрасываем половину.
- Память **`O(1)`** итеративно, `O(log N)` рекурсивно (стек вызовов).
- Бинарный поиск **по ответу**: `O(log(диапазон) × стоимость проверки)`.
  Например, если проверка — проход `O(N)`, суммарно `O(N log(max))`.

> ⚠️ Предварительная сортировка «чтобы применить бинарный поиск» стоит `O(N log N)` — это
> дороже, чем один линейный поиск `O(N)`. Сортировать ради **одного** поиска бессмысленно;
> имеет смысл ради **многих**.

## 📝 Эталонный разбор

### Задача A: классический поиск
Дан отсортированный по возрастанию массив `nums` без дубликатов и число `target`.
Верни индекс `target` или `-1`.

```js
function search(nums, target) {
  let left = 0;
  let right = nums.length - 1;          // ВКЛЮЧИТЕЛЬНАЯ правая граница

  while (left <= right) {               // <= потому что left === right — валидный отрезок
    const mid = Math.floor((left + right) / 2);

    if (nums[mid] === target) return mid;
    if (nums[mid] < target) {
      left = mid + 1;                   // mid уже проверен → +1, иначе зациклимся
    } else {
      right = mid - 1;
    }
  }

  return -1;
}
```

**Три вещи, которые нужно понимать, а не запоминать:**

1. **Почему `left <= right`, а не `<`.** Правая граница включительная (`nums.length - 1`).
   Отрезок из одного элемента — это `left === right`, и его ещё надо проверить. С `<` ты
   пропустишь последний кандидат.
2. **Почему `mid ± 1`.** Элемент `mid` уже сравнили, повторно рассматривать его нельзя —
   иначе при `left = mid` цикл может не сдвинуться и повиснуть навсегда.
3. **Почему `Math.floor((left + right) / 2)` безопасен в JS.** В C++/Java `left + right` может
   переполнить int, и там пишут `left + (right - left) / 2`. В JS числа — double, и до `2^53`
   переполнения нет. Знать про этот приём полезно (его любят спрашивать), но в JS он не нужен.

### Трассировка: ищем `5` в `[1, 3, 5, 7, 9]`

| шаг | left | right | mid | nums[mid] | действие |
|:---:|:----:|:-----:|:---:|:---------:|---|
| 1 | 0 | 4 | 2 | 5 | `=== target` → **вернуть 2** ✅ |

Ищем `4` (нет в массиве):

| шаг | left | right | mid | nums[mid] | действие |
|:---:|:----:|:-----:|:---:|:---------:|---|
| 1 | 0 | 4 | 2 | 5 | `5 > 4` → right = 1 |
| 2 | 0 | 1 | 0 | 1 | `1 < 4` → left = 1 |
| 3 | 1 | 1 | 1 | 3 | `3 < 4` → left = 2 |
| 4 | `left(2) > right(1)` — выход | | | | вернуть `-1` ✅ |

### Задача B: поиск **границы** (это важнее классики!)

Найти **первый** индекс, где `nums[i] >= target` (lower bound). Такой шаблон решает «первое/
последнее вхождение», «позиция для вставки», «первая плохая версия».

```js
function lowerBound(nums, target) {
  let left = 0;
  let right = nums.length;              // ИСКЛЮЧИТЕЛЬНАЯ граница — на 1 больше!

  while (left < right) {                // строгое <, границы разного типа
    const mid = Math.floor((left + right) / 2);

    if (nums[mid] >= target) {
      right = mid;                      // mid МОЖЕТ быть ответом → не отбрасываем его
    } else {
      left = mid + 1;                   // mid точно не ответ
    }
  }

  return left;                          // left === right — искомая граница
}
```

**Главное отличие от классики:** мы не ищем «равно», мы **сужаем область до границы между
"нет" и "да"**. Поэтому `right = mid` (без `-1`) — кандидат может оказаться ответом.

Ответ `left === nums.length` означает «все элементы меньше target».

> 💡 Держи в голове **два шаблона** и не смешивай их:
> - `while (l <= r)` + `r = mid - 1` + `return -1` → точное совпадение;
> - `while (l < r)` + `r = mid` + `return left` → граница.
> Смешение (`l <= r` вместе с `r = mid`) даёт **бесконечный цикл** — самая частая ошибка темы.

### Задача C: бинарный поиск **по ответу** (шаблон)

Пример постановки: «за сколько минимально часов в час Коко успеет съесть все бананы за `h` часов».
Массива для поиска нет — есть **диапазон возможных ответов** `[1, max(piles)]`.

```js
function minFeasible(low, high, isFeasible) {
  let left = low;
  let right = high;

  while (left < right) {
    const mid = Math.floor((left + right) / 2);
    if (isFeasible(mid)) {
      right = mid;          // mid работает → пробуем найти меньше
    } else {
      left = mid + 1;       // mid не работает → нужно больше
    }
  }

  return left;              // минимальный подходящий ответ
}
```

Алгоритм тот же самый; вся работа — **сформулировать `isFeasible`** и убедиться, что она
монотонна (если X подходит, то X+1 тоже).

## ⚠️ Частые ошибки / чек-лист

- ❌ **Бесконечный цикл** из-за смешения шаблонов или `left = mid` вместо `left = mid + 1`.
  Проверка: убедись, что **каждая** ветка гарантированно уменьшает отрезок.
- ❌ **Off-by-one в инициализации `right`:** `nums.length - 1` для включительной границы,
  `nums.length` для исключительной. Выбери шаблон и не путай.
- ❌ **`(left + right) / 2` без `Math.floor`** — получишь дробный индекс, `nums[2.5]` даст
  `undefined`, а сравнения молча пойдут не туда.
- ❌ **Забыть проверку `nums[mid] === target`** в классическом варианте.
- ❌ **Применять бинарный поиск к неотсортированным данным** без монотонного критерия.
- ❌ **Не проверить финальный ответ** в поиске границы: `left` может указывать за конец
  массива — обращаться к `nums[left]` без проверки опасно.
- ✅ **Всегда прогоняй руками массив из 1 и 2 элементов** — именно там ломаются границы.
  Это твоя личная точка роста: off-by-one уже встречались в two pointers и sliding window.

## ✅ Мини-опрос для самопроверки

1. Почему в классическом шаблоне условие `left <= right`, а в шаблоне границы — `left < right`?
2. Что произойдёт, если написать `left = mid` вместо `left = mid + 1`?
3. Как понять, что задачу можно решить бинарным поиском, если массив **не** отсортирован?
4. Какая сложность у «отсортировать массив, чтобы применить бинарный поиск» и когда это оправдано?
5. Чему равен `lowerBound([1,3,5], 6)` и что это значение означает?
6. Зачем в C++/Java пишут `left + (right - left) / 2` и нужно ли это в JS?

<details>
<summary>Ответы</summary>

1. Потому что различается **тип правой границы**. В классике `right` включительная
   (`length - 1`), и отрезок из одного элемента `left === right` ещё нужно проверить → `<=`.
   В шаблоне границы `right` исключительная (`length`), и `left === right` означает, что
   область сузилась до ответа → цикл должен закончиться, значит `<`.
2. Отрезок может перестать уменьшаться: при `left === right - 1` получим `mid === left`, и
   присваивание `left = mid` ничего не изменит → **бесконечный цикл**.
3. Нужно проверить **монотонность пространства ответов**: существует порог, до которого ответ
   «нет», а после — всегда «да». Если да — ищем этот порог бинарно, проверяя кандидата функцией
   `isFeasible`. Маркеры в условии: «минимальное/максимальное значение, при котором…».
4. Сортировка — `O(N log N)`, что **дороже** линейного поиска `O(N)`. Оправдано только если
   поисков будет много (`Q` запросов: `O(N log N + Q log N)` против `O(Q·N)`).
5. Вернёт `3` — длину массива. Это значит, что **все** элементы меньше `6`, и позиция для
   вставки — в самый конец. Важно: обращение `nums[3]` даст `undefined`, поэтому результат
   границы всегда проверяют перед разыменованием.
6. Чтобы избежать переполнения `int` при больших `left + right`. В JS числа — 64-битные double,
   и до `2^53` переполнения нет, поэтому `Math.floor((left + right) / 2)` безопасен.
   Знать приём стоит: про него любят спросить.

</details>
