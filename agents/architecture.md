# Архитектура тренажёра

Разделение материалов и приложения реализовано. Фактическую полноту функций и проверки
смотри в [статусе](status.md); схема ниже показывает границы ответственности.

## Структура

```text
algo/
├── agents/                    # Контекст разработки
├── content/                   # Учебные Markdown-материалы
│   ├── README.md              # Оглавление курса
│   ├── 00-how-to-solve.md
│   ├── 01-basics/ ... 08-js-interview/
│   ├── practice/
│   └── course.ts              # Каталог тем и связей с задачами
├── tasks/
│   ├── index.ts               # Единый реестр проверяемых задач
│   ├── types.ts               # Контракты функций/классов и оценки сложности
│   ├── validate.ts            # Проверка метаданных
│   └── <task-id>/
│       ├── task.ts            # Метаданные и способ проверки
│       ├── starter.js         # Код-заготовка ученика
│       └── cases.ts           # Проверочные случаи
├── src/
│   ├── app/                   # Инициализация, маршруты, темы
│   ├── pages/
│   ├── features/
│   │   ├── learning/
│   │   ├── practice/
│   │   ├── progress/
│   │   └── settings/
│   ├── components/            # Общие UI-компоненты
│   └── lib/
│       ├── content/           # Загрузка и обработка материалов
│       ├── runner/            # Изолированный запуск
│       └── storage/           # Хранение и перенос данных
├── personal/                  # Прежние личные решения и PROGRESS.md
├── package.json
└── README.md                  # О приложении и запуске
```

Приложение и описания тестов используют TypeScript, учебные решения — JavaScript.
Папки создаются по необходимости. Реестр обслуживает 99 задач с кодом и 2 мини-теста
(`tasks/quizzes.ts`). Каталог содержит 101 самостоятельное задание;
UI и runner получают описание по ID.

## Границы ответственности

| Часть | Ответственность |
|---|---|
| `content` | Теория, условия, подсказки и эталонные разборы |
| `tasks` | Стартовый код, тесты, вызов решения и сравнение результата |
| `src` | Представление курса, взаимодействие, выполнение и хранение |
| Данные браузера | Попытки, код, прогресс и настройки конкретного посетителя |
| `personal` | Архив владельца; не источник публичных заданий |

Условия не дублируются в тестовых описаниях. Связи строятся по стабильным ID.
Обычные функции, изменение входных данных на месте и последовательности вызовов
методов класса требуют соответствующих способов проверки.

## Перенос материалов

- Теория и практика переносятся вместе, сохраняя нумерацию и относительную структуру.
- Текущее оглавление становится оглавлением курса; корневой README описывает приложение.
- Личные попытки архивируются до очистки общих заготовок; ничего не теряется.
- Эталонные разборы остаются в курсе, скрытыми от случайного просмотра в интерфейсе.
- После переноса обновляются ссылки и инструкции. Личный архив в публичном репозитории
  не является приватным: исключение из сборки не скрывает его на GitHub.

## Выполнение кода

Код ученика выполняется в Web Worker внутри iframe с `sandbox="allow-scripts"` без
`allow-same-origin`: окружение имеет opaque origin. CSP ограничивает доступ к ресурсам
и сети. Длительность запуска и объём логов ограничены; отмена очищает окружение.
Исходники frame/worker из `src/lib/runner/` импортируются через Vite `?raw`:
iframe использует `srcdoc`, Worker — временный Blob URL. Каталога `public/runner/` нет.

Web Worker сам по себе не обеспечивает полноценную границу безопасности.
Доступ к сети, данным приложения и ограничение ресурсов нужно рассмотреть отдельно.
Не считать таймаут защитой от всех случаев чрезмерного расхода памяти.

Запуск, его состояние и диагностика отделены от редактора. Таймаут, ошибка инфраструктуры
и неполный запуск не засчитываются. Это не anti-cheat: враждебный код внутри Worker может
пытаться подделывать результаты, а тесты доступны на клиенте.

`runTask(taskId, code, signal?)` всегда выполняет полный набор тестов из реестра. Прогресс отмечается
после `passed`. Поле `mode` в сохранённых попытках оставлено ради совместимости старой
истории/экспорта (`example`); новые попытки используют только `check`. Отметка историческая:
изменённый код требует повторной проверки. В IndexedDB сохраняются текущий черновик,
оценки сложности и последние пять запусков со снимками кода. Записи сериализуются,
чтобы быстрые правки не перезаписывали более свежий черновик старым.

Маршрутизация использует hash, сборка — относительный base для статического размещения.
Markdown загружается лениво только из `content/`; raw HTML проходит sanitization.
Личные решения не импортируются в приложение.

`src/lib/content/navigation.ts` группирует каталог по восьми разделам и задаёт номера
«раздел.тема» вместо прежнего сквозного счётчика 1–22. Эту модель используют sidebar,
каталог и навигационная строка. `CourseSidebar` хранит раскрытие разделов/тем в состоянии
компонента как два ID или null: одновременно открыты не более одного раздела и одной
темы. Переключение раздела сбрасывает вложенную тему; закрыть можно и последнюю ветку.
Название темы — ссылка на теорию: при выборе другой страницы открывает
теорию и список, на текущей странице темы повторный обычный клик только переключает
раскрытие через preventDefault (без новой записи истории). Стрелка переключает список
независимо от навигации; modifier-click сохраняет обычное поведение ссылки.
Название раздела аналогично ведёт на обзор `/section/:sectionId`; повторный клик на
этом обзоре переключает раскрытие без навигации. Стрелка раздела — отдельная кнопка.
Компонент заменяет раскрытую ветку активными предками только при переходе к разделу/теме/задаче
(включая историю браузера) и не сбрасывает ручное
сворачивание на той же странице. Скролл активной ссылки ограничен самой боковой панелью.
Главная `/` — `WelcomePage`: идея курса, порядок работы, наставления и локальное
хранение; логотип ведёт на неё. Каталог `CoursePage` перенесён на `/topics`,
все ссылки возврата к курсу и корень breadcrumbs ведут в каталог.
Обе страницы используют `usePageStart`: сброс window-scroll в layout effect
и временный `history.scrollRestoration = manual`, восстановленный при уходе.
Каталог `/topics` и главная открываются со свёрнутыми ветками. Возврат к каталогу и обычный повторный
клик «Все темы» сбрасывают раскрытие; повторный клик не добавляет запись в историю.
`SidebarResizer` использует Pointer Events с capture и клавиатурный separator.
Ширина 200–400 px (по умолчанию 228) хранится числом в `algo-sidebar-width-v1`;
ошибки чтения/записи показываются явно. CSS-переменная `--sidebar-width` синхронно
меняет фиксированное меню и колонку shell без размонтирования страниц.
До 900 px разделитель скрыт, меню сверху; desktop-ширина не перезаписывается.
Идентификаторы задач и хранилище прогресса от нумерации не зависят.
Каждый раздел имеет `overviewPath = <folder>/README.md`: Markdown загружается лениво
тем же loader. `SectionPage` показывает обзор и маршрут из каталога с переходом
к первой теме. Заголовки групп каталога и родитель в breadcrumb ведут на обзор.
Markdown-ссылки на README разделов (или их директории) разрешаются в section-маршруты.
`findCourseLocation` для обзора возвращает раздел и его номер без темы.
Для задания возвращается также `task`; `number` по-прежнему обозначает тему,
а номер задания берётся из `getTaskNumber`. Breadcrumb показывает раздел и тему
как ссылки, затем номер и название текущего задания без ссылки (`aria-current`).
Одинаково для кодовых задач, split-частей и квизов.
Номер задачи — `раздел.тема.позиция`, вычисляется тем же модулем по порядку каталога
и используется в меню, практике и кодовых/quiz-страницах. Суффиксы имён split-файлов
не участвуют в нумерации. `content/priorities.ts` читает лёгкое оглавление практики,
а не загружает все решения: 🔴/⚪ — единственный источник приоритета для UI.
Отсутствующие/повторные объявления отвергаются, явные заголовки Markdown сверяются тестом.

Оценка сложности описывается метаданными задачи (`ComplexityDefinition`): варианты,
четыре критерия Range Sum Query или два критерия функции, целевые значения и пояснения.
`accepted` задаёт дополнительные явно допустимые оценки; сравнение не доказывает
сложность реализации. Выбранные ID хранятся
в необязательном `TaskRecord.complexityChoices`. Снимок кода и выбора создаётся до
запуска runner; сверка не зависит от времени завершения автосохранения и не обновляется
при клике на карточку. После неуспешного запуска сравнения нет. После успешного —
сверяется снимок с целью и проверяется его актуальность относительно текущего кода/выбора.

Формат экспорта повышен до версии 3; импорт принимает 1, 2 и 3. Старые записи IndexedDB
без `complexityChoices` читаются как незаполненные. `timeComplexity` и `spaceComplexity`
сохранены как прежние текстовые заметки, показываются read-only и не угадываются из текста.
Схема object store не изменилась; отдельная миграция базы не требуется.
Результат сверки не хранится как подтверждение сложности кода.

Мини-тесты используют те же стабильные ID и хранилище: необязательные `quizAnswers`
и `quizExplanations` присутствуют в текущей записи и снимках попыток. Legacy code и
текстовые оценки не удаляются. Проверяется выбор варианта, не качество свободного текста.

## Реестр и контракты задач

`TaskDefinition.runner` — дискриминируемое объединение:

- `function`: имя функции, список аргументов, ожидаемый JSON-результат, выбор возвращаемого
  значения или изменённого аргумента, стратегия сравнения;
- `class`: имя класса, списки аргументов для экземпляров, последовательность методов
  с аргументами и ожидаемыми значениями, чтение свойств; `ignoreReturn` для неоговорённого
  возврата и `expectedUndefined` для строгого ожидания `undefined`;
- `linked-list`: значения узлов, позиция цикла, дополнительные аргументы, ожидание
  значения/ссылки на узел/списка. Отдельные случаи могут вызывать другой `entryPoint`
  (в текущем каталоге самостоятельные части разделены);
- `binary-tree`: compact level-order, аргументы-узлы по индексам токенов,
  ожидаемые значения, identity узла или структура дерева;
- `graph-clone`: список смежности, значения и корень; новая структура без ссылок
  на исходные узлы/массивы соседей и без нескольких копий одной вершины;
- `scenario`: доверенный асинхронный script-body проверяет экспортированную функцию/класс
  через реальные callbacks, Promise, виртуальные часы и mock-зависимости.

`worker-source.ts` внедряет scenario-runtime в лексическую область Worker. Сценарии
компилируют решение заново для каждого случая, сбрасывают таймеры/зависимости и используют
MessageChannel для реальных checkpoints микрозадач. Подменены таймеры, Date и performance.now;
сеть заменена стабильным fetch-proxy. loadData/render/showError — явные mock-зависимости.
Assertions не теряются, даже если callback их перехватил; unhandled rejection — ошибка.
Непроверенный сценарий без assertions не считается успешным.

`scenario-test-support.ts` исполняет только доверенные test fixtures в отдельных Node
worker_threads с deadline. Он не импортируется приложением; пользовательский код
выполняется исключительно браузерным sandbox. Обычный runner загружается лениво по
нажатию проверки; страницы квизов не загружают Monaco или sandbox-исходники.

TreeNode и Node предоставляются только соответствующим адаптерам через лексическое
окружение решения. Дерево строится очередью непустых родителей, не heap-индексами.
Проверка возвращённого дерева ограничена ожидаемым числом узлов и запрещает циклы/общие
поддеревья. Clone Graph проверяет identity, независимые массивы и topology, игнорируя
порядок соседей. Необязательная сохранность дерева задаётся `preserveInput`.

Для класса `factories` задаёт доверенные фабрики компараторов по номеру экземпляра
и аргумента (числа или числовое поле объекта, asc/desc). `factoryMethod` вызывает
статический создатель экземпляра вместо `new`, `preserveArgs` защищает исходные данные.
Функции-компараторы создаются в Worker, а не передаются через structuredClone.
В отчёте длинной последовательности отдельно указан первый несовпавший вызов.

ListNode создаётся внутри Worker и доступен решению через лексическое окружение.
Узлы не пересылаются обратно в UI: отчёт содержит ограниченное текстовое представление.
Для `node` важна identity; для `list` — значения, отсутствие цикла и, при необходимости,
исходные узлы/порядок. Не навязывать сохранность входа, если условие её не требует.
Обход выходного списка ограничен ожидаемой длиной и обнаруживает повторные ссылки.

Вызовы класса с `ignoreReturn` не требуют строго `undefined`: допустим и неиспользуемый
возврат. Их эффекты наблюдаются через вызовы с `expected`; валидатор запрещает сценарии
с одними лишь непроверяемыми возвратами.

Для функций поддержаны точное сравнение, неупорядоченный массив примитивов и
неупорядоченные группы примитивов. Сравнение не сводится к строке JSON и не теряет
типы, дубликаты или границы групп. При необходимости проверяются неизменность указанных
аргументов и новый выходной массив. Проверка аргументов использует независимые копии.
`unordered-tuples` сохраняет внутренний порядок пар. `closest-points` проверяет
мультимножество исходных точек и совпадение отсортированных расстояний с k наименьшими:
это допускает граничные ties, но не позволяет пропустить строго более близкую точку.
`topological-order` проверяет перестановку и зависимости, а пустой ответ — наличие цикла.
`approximate` использует объявленную погрешность для конечных чисел. FunctionCase может
явно ожидать `undefined`; это не `null` и не отсутствующий контракт.

`content/course.ts` вычисляет `runnable` по реестру, страница выбирает то же определение.
Неизвестный ID runner возвращает явную ошибку, а не подставляет Range Sum Query.
Черновик, история и карточки остаются привязаны к ID; данные старой задачи не мигрируют.
Тестовые реализации в `tests/fixtures/` не импортируются в приложение.

## Разделение самостоятельных частей

Все прежние 79 ID и пути сохранены за первыми частями. 22 новые части получили свои
ID/Markdown и `CourseTask.previousTaskId`. Helpers и альтернативные алгоритмы одного
результата не становятся новыми задачами. Код и история не переносятся автоматически.
В новой исполняемой части можно подтвердить копирование прежнего кода; исходная запись,
история и отметка успеха не меняются, новый успех требует собственной проверки.

Throttle leading и leading + trailing разделены как разные контракты вывода.
Два задания Event Loop — мини-тесты: сниппеты/разборы извлекаются из исходного Markdown
с учётом fenced blocks. Разбор не показывается для нетронутых вопросов. Ответы output-order
дополнительно проверены реальным выполнением неизменяемых сниппетов в браузерных тестах.

`CaseResult.logs` содержит вывод конструкторов и методов конкретного теста,
`RunResult.logs` — вывод до тестов. Бюджет вывода общий для всех групп, валидатор
проверяет и локальные поля, и суммарные ограничения. `logsTruncated` сообщает о сокращении.
При исключении текущий кейс остаётся в отчёте со своими логами и ошибкой;
следующие кейсы не запускаются. При отмене/таймауте частичный отчёт не передаётся.

## Рабочие панели

`WorkspacePanels` использует плоский CSS Grid со стабильными дочерними панелями.
Пресеты меняют только положение и размеры, не родителей компонентов. Свёрнутые и
временно скрытые панели остаются смонтированными — это сохраняет модель Monaco и undo.
Панель редактора содержит прокручиваемый `editor-workflow`: код и затем карточки оценки.
Кнопки проверки/остановки вынесены за эту прокрутку. Минимальная высота canvas сохраняется
при открытии карточек; результат сверки остаётся в панели результатов, история — под панелями.
Минимальные размеры, Pointer Events с capture и клавиатурное управление реализованы
в разделителях. Новых библиотек компоновки нет.
Три контурные SVG-кнопки выбирают пресет напрямую; четвёртая сбрасывает схему,
размеры и свёрнутые панели. `aria-pressed` отражает сохранённый пресет для широкого
экрана. Подсказки доступны по hover и клавиатурному фокусу, Escape при фокусе скрывает их.

Схема, размеры по пресетам и свёрнутые панели хранятся под ключом `algo-workspace-v1`.
Формат данных — v2: `sizes.stacked` содержит независимые целочисленные высоты в px,
а `columns`/`bottom` по-прежнему проценты. Parser принимает v1 и пересчитывает
вертикальные пропорции по доступной высоте контейнера при загрузке, учитывая минимумы.
Следующее изменение сохраняет v2 под тем же ключом.
Вертикальный Grid имеет автоматическую общую высоту и три разделителя — после
каждой панели. Растягивание меняет только высоту верхней панели, сдвигая всё ниже;
минимумы — 140/220/140 px, без ограничения высотой viewport. Для drag используется
координата страницы, чтобы прокрутка не ломала расчёт; scroll anchoring отключён
на время перетаскивания. Paired-resize в остальных схемах не изменён.
При ширине рабочего места менее 640 px используется вертикальная схема без изменения
выбора для широкого экрана. Maximized-панель — временное состояние, не настройка хранения.
Повреждение настроек и ошибки localStorage отображаются явно.

Monaco 0.57 требует регистрации `features/register.all` до создания первого редактора.
Без неё поздняя загрузка contributions приводила к UNKNOWN service при повторном входе.

## Расширение: ИИ-наставник (не реализуется сейчас)

Редактор выбран: Monaco. Код решения и результаты выполнения должны быть доступны
на уровне состояния приложения, а не только внутри редактора или его DOM. Это позволит
в будущем передавать выбранный контекст наставнику без переделки runner.

В компоновке учитывается сворачиваемая панель диалога рядом с рабочим местом.
Точное расположение на узких экранах пока не выбрано. В первой версии не нужны
пустая панель, неработающая кнопка ИИ или система плагинов.

Предлагаемые границы для будущей реализации, требующие отдельной проработки:

- Наставник получает явный снимок контекста: задачу, выбранный код, при необходимости
  результат соответствующего запуска и вопрос ученика. Снимок позволяет отличать
  обсуждаемый код от последующих правок.
- Перед отправкой пользователь видит, какие данные и какому провайдеру передаются.
  Эталонный разбор и весь архив попыток не добавляются автоматически.
- Доступ по умолчанию — чтение и объяснение. Изменение кода и запуск требуют
  отдельного действия пользователя; сообщения ИИ не определяют прохождение тестов.
- Интеграция провайдера отделяется от UI и runner. Наличие подписки не означает наличие
  API-доступа; авторизация и возможная серверная часть рассматриваются позже.
- Ключи и токены не входят в контент, сборку сайта, экспорт прогресса или контекст модели.

Сейчас сохраняем границы модулей и возможность расширения компоновки, но не создаём
абстрактные SDK, адаптеры провайдеров и дополнительные зависимости заранее.
